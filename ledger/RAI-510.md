# RAI-510 — 上限语义只落在直接被 kill 的那一层

> 票: RAI-510。合并: PR `capy/rai510-timeout-scope`。

### 2026-11-26 RAI-510: 超时整组回收 + job 级预算 + compile-only 也设上限

- 提交: d6271ad

三条同源缺陷, 都是「上限只落在直接被 kill 的那一层」:

1. **超时留孤儿 (最坏)**: `subprocess.run(timeout=…)` 只终止直接子进程, `cargo test` 派生的
   测试二进制与 daemon 变成孤儿留在 runner 上, 污染同 job 后续 target —— 今天 `control_websocket`
   挂死把 `restored_index_*` 拖下水就是这条。改成子进程进独立进程组 (POSIX
   `start_new_session` + `killpg`, windows `taskkill /F /T /PID`), 超时后整组回收。
2. **每 target 1500s 不是 job 级预算**: 两次挂起就把 60 分钟 job 撑爆。新增
   `JOB_BUDGET_SECONDS` (默认 3300s, env 可覆盖) 与 `BUDGET_FLOOR_SECONDS`, 每个 target 的实际
   上限 = min(单 target 上限, 剩余预算); 预算耗尽时**判红并点名未执行的 target**, 不是静默跳过。
3. **compile-only 的 `--no-run` 没有上限**: 同样会挂 (链接/依赖解析), 同样无名字。现在共用上面
   两个上限。

验证 (判据是进程回读, 不是「代码里加了 kill」):

- 旧做法负对照: `subprocess.run(timeout=2)` 跑「bash 派生 python 睡 300s」→ 超时返回后
  `pgrep -af <marker>` 仍有 **1 个存活** (孤儿子进程)。
- 新做法: 同一命令 `run(timeout=2)` → `exit 124`, 日志 `已整组终止 (killpg <pgid>)`,
  `pgrep` 存活 **0**。
- 预算: `RDOG_JOB_BUDGET_SECONDS=1` 跑 `--os windows-latest` → `job 预算 1s 不足, 未执行:
  computer_use_density` 并判红 (同时触发「零执行」守卫)。

**已知边界 (写下来而不是假装没有)**: 子进程若自己 `setsid`/双重 fork 逃出进程组, `killpg` 抓不到
它。rdog 自己的 daemon 不这么做; 真遇到时按 `docs/solutions/logic-errors/gnu-coreutils-kill-neg-pid-argument-ambiguity.md`
那套「按 PID 回读确认」的方式再补。

### 2026-11-26 RAI-510 评审 F1–F7 (七条全是同一形状: 修的东西自己漏了一处同形的洞)

- 提交: 20a9ab1

**F1 (high) `_kill_tree` 先看 `proc.poll()`**: 直接子进程先退出就 `return "already exited"`,
后代继续活着 —— 那正是孤儿的定义。评审用本函数实测: 形状 A(中间退出、孙进程同组握管道)
存活后代 1, 形状 B(中间活着) 0。同处 `os.getpgid()` 在 leader 已回收时抛 `ProcessLookupError`
也被当成「组没了」。修: spawn 时固定 `pgid = pid`, 无条件 `killpg`, 只有 `ProcessLookupError`
当「组确实没了」, 并**回读** `/proc` 里该 pgid 的存活成员 (排除僵尸)。

**F2 (high) windows 上要杀的对象在树外**: `rdog daemon` 默认重开成 `hidden-daemon --child`
(`CREATE_NO_WINDOW|DETACHED_PROCESS`), `taskkill /T` 够不着。修: 跑 target 时统一注入
`RDOG_DAEMON_FOREGROUND=1`; `taskkill` 返回码非 0 时把 stderr 写进日志并判失败。

**F3 (high) 预算与 job 真实剩余时间无关**: 3300s 是「本步开始 + 常数」, 而 job 60 分钟、前缀
(checkout/cargo-prep/unit tests) 实测 ubuntu 88–103s / macos 149–167s / windows 203–239s, 依赖一改
还会更久 → 必然越过 3600 被 cancel。修: job 第一个 step 写 `$RUNNER_TEMP/job-started-at`, 脚本按
`job_timeout − elapsed − 180s 余量` 算 deadline。

**F4** 超时后 `communicate(timeout=30)` 拿不到输出时, 原写法把已收到的证据整段丢弃 → 现在把
`TimeoutExpired.output` 拼回 partial。**F5** 预算耗尽与「零执行」同时判红、且 `return 1` 早于写
summary → 零执行守卫在预算已报时让位, summary 先写后判。**F6** 剩余不足按预算口径 skip, 不再给
「121s 截短上限」(会把慢而健康的 target 记成挂死); 截短提示只在真的截短时出现。**F7** 文档比代码
承诺得多 → 现在**真的回读** (POSIX 读 `/proc`; windows 明确写「无回读, 只看返回码」)。

验证 (形状 A 与 B 都跑了):

| 形状 | 旧实现 | 新实现 |
| --- | --- | --- |
| A 中间进程先退出、孙进程同组 | `already exited` → 存活 1 | `killpg …, 回读 0 存活` → 存活 0 |
| B 中间进程活着 | `killpg` → 存活 0 | `killpg …, 回读 0 存活` → 存活 0 |

预算派生: job 起点 3500s 前 + 60min → `剩余 -90s` → 判红并点名; 120min → `剩余 3519s` → 正常跑。

### 2026-11-26 合入后立刻暴露的时序缺陷: 宽限 3 < 一次合并的提交数

- 提交: 待合入后补 (标题: `fix(bookkeeping): 宽限窗口内占位算待补 + 默认宽限 10 (合入后 main 立刻红的根因)`)

#169 合入 main 后, main 的 `knowledge carriers` **立刻红** (`漏记账: 3`): 那个 PR 有 5 个工作
commit, 而宽限只有 3 —— 剩下 2-3 个在 sha 补齐 PR (`#170`) 到达之前就已经「超期」。也就是说
时序补丁本身有个窗口比一次合并还窄的洞, **而它是被真实 main 跑出来的**, 不是推演出来的。

修法两条:

1. **宽限窗口内的占位算「待补」而不是漏账** (原来 main 模式一律不接受占位): 否则任何提交数 >
   宽限的 PR 一合入就把 main 弄红;
2. **默认宽限 3 → 10**: 覆盖一次合并自带的提交量; 超出宽限还留着占位 → 「占位超期」判红
   (文案写明"sha 早已稳定, 该补了")。

**再进一步 (二轮复核后)**: 位置宽限这个量天生要追着最大的合并跑 (main 最近 12 次合并的工作 commit 数
1–26 不等), 抬到 10 也只是把阈值挪个位置。所以占位的超期判据改成**时间**: 占位 commit 的提交时间
超过 `--max-placeholder-age-days` (默认 3 天) 才判「占位超期」, 位置宽限只留给「完全没有账本条目」
的 commit。

实测 (临时仓, 两个方向都造了):

| 形状 | 读数 |
| --- | --- |
| 占位 commit 的 date 是 **5 天前**, 数量在宽限内 | `漏记账: 1` + `原因: 占位超期 5.0 天 (上限 3 天)`, exit 1 |
| **12 个**今天日期的占位 (远超数量宽限 10) | `占位待补 sha: 12` 逐条可见, `漏记账: 0`, exit 0 |

也就是: 任何规模的合并合入当天 main 必绿; 「忘了补 sha」在 3 天后一定被抓。

### 2026-11-26 RAI-510 五轮复核: 年龄的参照点错了 (长寿命分支假阳性)

- 提交: 待合入后补 (标题: `fix(bookkeeping): 占位年龄从「落 main」起算 (RAI-510 五轮复核)`)

从 commit date 算年龄会让**长寿命分支**吃假阳性: 一张活了一周才合的分支, 合入当天它的占位年龄
就是 7 天, main 立刻红 —— 而 sha 昨天根本不在 main 里。判据参照点选错了, 不是频率问题。

修: `commit_landed_epoch()` 找 `sha..HEAD` 的 ancestry-path 里**最早的 merge** (即把它带进
main 的那个合并) 取它的 committer date; 找不到 merge (直接推 main 的 commit) 才退回 commit date。
`(占位待补) … (落 main 已 N 天)` 把这个参照点显式打出来。

两个负对照 (都造了):

| 形状 | 读数 |
| --- | --- |
| commit date **7 天前**, 今天才 `--no-ff` 合入 main | 绿, `(落 main 已 0.0 天)` —— 证明参照点是落点不是 commit date |
| 同一 commit, 合入那一步的 date 拨到 **5 天前** | 红, `占位超期 5.0 天 (上限 3 天)` |

只造第二条的话用 commit date 也能过, 等于没验; 两条一起才钉住「从落 main 起算」。

### 2026-11-26 RAI-510 六轮复核: 参照点会挑错「同步 main」的 merge

- 提交: 待合入后补 (标题: `fix(bookkeeping): 落点只认一线父链 + merge commit 全模式排除 (RAI-510 六轮复核)`)

在 `sha..HEAD` 里找最早 merge 会把**评审期把 main 同步进本分支**的那个 merge 当成落点 (它更早)。
本仓近 35 次合并里有 4 次是这种同步 merge, 所以触发面是真的。**一个 commit 在分支里被 merge 过
多少次, 和它什么时候落到 main 上, 是两件事**: 前者是分支历史, 后者才是 main 的历史。

修: 只认 HEAD 的**一线父链** —— 链上「最早的、以 sha 为祖先的那个 commit」就是落点 (同步 merge 不在
链上, 自然排除; 直推 main 的 commit 本身就在链上)。「包含 sha」在一线父链上单调, 所以二分查找即可。
后缀区分两种参照: `(落 main 已 N 天)` / `(按 commit date N 天)`。

**另一个结构性缺陷**: 本地 strict 在 `origin/main` 上默认红 —— `48970f9`/`9101c85` 两个 merge commit
「未进账本」, 而 merge commit 的 sha 在它被创建之前不可能出现在账本里。要求它记账是逻辑上做不到的
事, 训练出来的只是「反正它红着」。现在 **merge commit 在所有模式下都排除**。

三个形状 (都造了):

| 形状 | 读数 |
| --- | --- |
| W 7 天前 → 分支内 `merge main`(5 天前) → 今天落 main | 绿, `(落 main 已 0.0 天)` |
| 5 天前**直推** main + 今天别的分支合并 | 红, `占位超期 5.0 天` (参照点取的是链上那个直推 commit) |
| 本地 strict 在 `origin/main` 上 | exit 0 (merge commit 不再要求记账) |

### 2026-11-26 RAI-510 七轮复核: 参照点必须自证, 而且不能每占位跑两遍

- 提交: 待合入后补 (标题: `fix(bookkeeping): 参照点带 sha 自证 + 一线父链只取一次 (RAI-510 七轮复核)`)

1. **「不再父链上」这个分支原本构造上不可达, 却会打出假话**: `--main` 下 scope ⊆ ancestors(HEAD),
   而 HEAD 恒在自己的父链上, 所以 `landed is None` 实际不会发生; 真正会发生的是「挑了个分支内的
   同步 merge 当落点」, 而输出只写天数, 读的人无从发现。修: 后缀带上**参照 commit 的短 sha** ——
   `(落 main 已 N 天, 参照 <sha>)` / `(未在一线父链上找到落点, 按 commit date N 天)`。
