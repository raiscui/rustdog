# RAI-592 账本

`request_timeout_ms` 在本地 unixpipe fast path 上「不生效」。定性结果: **不是 fast path 的问题,
是 60s 地板, 且与 transport 无关** —— 一条隐藏契约, 载体里没写。

## 2026-11-27 把 60s 地板写进用户可见载体

- 提交: 待合入后补 (标题: `docs(control): 写清 line-control 的 60s 响应地板与 request_timeout_ms 的两副语义 (RAI-592)`)

源码是唯一真相: `src/zenoh_control/client_pty.rs:30` 的 `LINE_CONTROL_RESPONSE_TIMEOUT = 60s`,
`:544` 取 `60s.max(timeout)`; 这个 `execute_remote_request` 被 unixpipe / tcp / websocket 共用,
所以**行为与 transport 无关**。`request_timeout_ms` 只能抬高、永远压不到 60s 以下。

实测 (`request_timeout_ms = 3000`):

| 命令 | 结果 |
| --- | --- |
| `sleep 5; printf SLOW5` | 成功, 5046ms |
| `sleep 62; printf LATE` | exit 1, 60050ms, `Zenoh session bridge 在 60000ms 内未收到 final @response` |

处置按「写清」而不是「对齐」(对齐会改既有行为, 而 60s 地板看起来是刻意的: line-control 上跑的
是 `@cmd`/`@script` 这类真实长命令):

- `specs/code-agent-rdog-control-usage.md` 新增「超时: line-control 的响应等待有 60s 地板」一节:
  写清源码指针、两副语义 (解析目标/建 bridge 用 `request_timeout_ms`; 等 `@response` 不)、
  实测两行, 以及**本地长命令靠什么防止无限等** (命令自己的超时, 不是调小参数)。
- 同文件配置示例里 `request_timeout_ms = 3000` 加了注: 它是地板不是总预算 —— 照抄示例的人
  原本会以为 3s 生效。

顺带修正: 我最初把这条归因为「fast path 不生效」, 机制是错的 —— 与 transport 无关。
