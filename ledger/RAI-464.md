# RAI-464 — ubuntu CI 的 code 70 归因订正 + `tls_init` 并发写坏 TLS 材料

> 票: RAI-464 (镜像 issue #163)。合并: PR `capy/rai464-ubuntu-ci-e2e`。

### 2026-11-26 RAI-464: code 70 不是「control client 连不上 daemon」, 是 enigo 连不上 display

归因订正。`@response {"id":7,"code":70,"error":"no connection could be established:
(no successful connection)"}` 里那句话是 **enigo 的原文**
(`enigo-0.6.1/src/lib.rs:437` 的 `NewConError::EstablishCon`, 由 `src/linux/mod.rs:117`
在「x11 / wayland 都没连上」时返回), 与 control client 到 daemon 的连接、端口、回环地址、
local-default fast path 都无关。ubuntu runner 没有 `DISPLAY`, 开发机有 (Xvfb `:9`) —— 这就是
「本地绿 CI 红」的全部差别。

判据 (同一二进制, 只切一个变量; 当时用例还带 `#[ignore]`, 所以要用 `-- --ignored`, 撤掉后
直接跑即可):
- `env -u DISPLAY cargo test --test control_lanes daemon_control_lane_should_accept_key_object_payload_with_request_id`
  → 0.07s 失败, 打印同一句 code 70;
- `DISPLAY=:9` / `xvfb-run -a` 同一命令 → 通过 (`xvfb-run` 下整个 target 15 passed / 1 ignored,
  `env -u DISPLAY` 下恰好只有这一条红)。

修法是给环境补前提, 不改断言: `ci.yml` 的 `test-ubuntu`「Integration targets」步骤包一层
`xvfb-run -a --server-args="-screen 0 1280x1024x24"`; `control_lanes` 那条 linux 专属
`#[ignore]` 撤掉。口径同 `tty-term-dumb-environment-deterministic-failure.md`:
固定测试假设的环境, 而不是放宽断言或延长时间。
- 提交: 待合入后补 (标题: `fix(e2e): ubuntu 的 integration 步骤在虚拟 X display 下执行, 撤 control_lanes 的 linux ignore (RAI-464)`)

### 2026-11-26 RAI-464: `tls_init` 并发把两套 CA 交错写进同一目录

`tls_init` 的「已初始化」判据是 `tls_dir.exists()`, 而目录先建、六个文件后写: 两个并发
`rdog auth tls-init` 要么都生成 (两份 CA 的证书交错落盘: daemon 证书签自 CA-A 而 `ca.pem`
来自 CA-B), 要么后者看到空目录就跳过、留下半套材料。两种结局都让 TLS/mTLS 握手必然失败,
症状就是 `zenoh_router_client` 的 TLS/mTLS 用例「client 建不上到 daemon 的连接」。

负对照 (先造红): 新增并发单测 8 线程同时 `tls_init` 同一目录, 旧代码实测 `created=2`,
判据「只能有一方生成完整材料」成立。改法: 先在唯一暂存目录写完六件, 再整目录 `rename`
到位 —— 「目录存在」因此等价于「材料完整」, 落败方按已初始化跳过并收走暂存目录。
实测: `cargo test --test zenoh_router_client tls` 修复前 11 轮红 4 轮 (两例同挂, 20.6s 等 ack),
修复后 6 轮未再观察到该家族复现 (这 6 轮只说明"没再红", 因果以并发单测为准 —— 另一族首帧竞态
仍有约 1/3 的命中率, 见下一条)。
- 提交: 待合入后补 (标题: `fix(tls): tls_init 改整目录原子落地, 并发只允许一方生成材料 (RAI-464)`)

### 2026-11-26 RAI-464: 剩下的 TLS 首帧竞态在 zenoh 链路层, 记进 #163 不硬修

`tls_init` 修完后, `zenoh_router_client` 全 target 仍有约 1/3 轮命中一次 TLS/mTLS 失败。
拿到两侧 debug 日志 (`RDOG_LOG_LEVEL=debug`) 后的机制:

- daemon 侧: `TX task failed: handshake not complete at zenoh-link-tls-1.8.0/src/unicast.rs:203`
  —— 链路已经 `New transport opened`, accept 也打了 `Accepted TLS connection`, 但首帧写入时
  rustls 仍认为握手未完成, zenoh 随即关链路;
- client 侧: `RX task failed: peer closed connection without sending TLS close_notify`;
- 相邻还有一次 `received fatal alert: DecryptError`。

也就是说 `zenoh-link-tls` 1.8.0 把链路交给 transport 的时间早于 rustls 握手完成的时间,
首个写入方 (可能是 daemon 的 reply) 会丢掉这一帧。这在**串行**跑 (`--test-threads=1`) 也复现,
所以不是测试并发互相干扰, 与 runner 无关。修复要落在 zenoh 链路层或 rdog 的链路就绪时序,
不在本票范围内 —— `zenoh_router_client` 在 ubuntu 的整片豁免因此**保留**, 理由从「client 连不上
刚启动的 daemon」改写成这条实测机制, 收回条件留在 issue #163。

同时按 #163 的验收第 3 条给两条 TLS 用例补了失败自证: 断言失败时把 daemon 采集到的
stdout+stderr 打进 panic 文案, 否则下一轮 CI 上仍然只有空 stdout。
- 提交: 待合入后补 (标题: `docs(ci)+test(e2e): 订正 ubuntu 豁免理由并给 TLS 失败补 daemon 日志 (RAI-464)`)

### 2026-11-26 RAI-464 评审必修: 并发单测的判定面扫到了进程级共享目录

只读评审 (gpt-6.2-sol, 独立机器) 抓到四条, 其中一条是本次改动**引入的假红源**:

1. **（severe）** 并发单测的「暂存目录残留」断言扫 `temp_dir()` 并按 `contains("staging")` 过滤 ——
   同二进制里兄弟用例的 `<...>.staging-*` 同样命中, 实测 60 轮挂 8 轮。它落在三个平台都跑的
   unit test 步骤上, 等于给所有人的合并门制造随机红。改成只扫本用例自持的父目录
   (`<root>/tls` 作为 tls_dir, 只数 `<root>` 下的非 `tls` 项)。
2. `tls_init` 的「目录存在 = 材料完整」对旧版本留下的半套目录不成立 (旧实现边建目录边写文件,
   崩溃即半套, 而半套材料做 TLS 握手必失败、排查会被引向「证书不对」)。补完整性判据:
   六件不齐就 fail closed 并点名缺失项, 不覆盖用户材料。新增与调度无关的确定性用例
   `tls_init_should_reject_incomplete_existing_material` (并发用例只在 ≥2 核上有判别力)。
3. 知识载体两处事实错误: §3b 的 `#[ignore]` 计数写成「只剩三处」(实际 `tests/` 下 20 处,
   CI 会执行的 target 里 4 处), 且把 `zenoh_router_client` 那条历史上的 `#[ignore]` 说成
   「platform ignore」; §6 的已知红表还留着已被推翻的「一族不稳定 / client 连不上」归因,
   与同文 §3b 打架。两处都按实测重写, §6 那行明确拆成两族。
4. 失败自证只覆盖了 5 条断言里的 2 条, 而本地两次复现都挂在没补的那条 (`zenoh_router_client.rs:3292`
   `CA client 应经 tls 连通`) —— 补齐到全部 5 条。

小项一并收:`xvfb-run` 的安装兜底连带装 `xauth` (`xvfb-run` 缺 `xauth` 时 `exit 3`);
暂存目录名从「pid + 纳秒」改成 `create_dir` 独占创建 + 进程内计数器重试 (唯一性要是机制,
不是同纳秒不撞的巧合); `specs/rdog-tls-plan.md` 记下原子发布契约与 `client/` 路径。
- 提交: 待合入后补 (标题: `fix(tls): 完整性 fail closed + 暂存目录独占命名, 收评审四条 (RAI-464)`)

### 2026-11-26 RAI-464 裁定落地: 豁免收窄成具名跳过 + tls_init 覆盖边界

Captain 的裁定是「A, 但先试一次把豁免收窄」, 并要一条 `tls_init` 的覆盖边界证据。

① **豁免收窄**: 撤掉 `PLATFORM_EXEMPTIONS` 里 `zenoh_router_client` 在 ubuntu 的整片豁免, 换成
新增的 `TARGET_TEST_SKIPS` —— target 照常执行并计入 ran 集合, 只按名字跳过那 2 条 TLS 用例
(`tls_enabled_daemon_should_serve_ca_client_and_reject_wrong_ca`、
`mtls_daemon_should_require_client_certificate_and_accept_configured_client`)。名字进 job summary,
并且脚本用 `cargo test --test <t> -- --list` 验证名字真实存在 —— **负对照**: 把其中一个名字写错
一个字母, 脚本 `exit=1` 并点名 `具名跳过的用例在 target 里不存在`。本地回执: ubuntu 从 10 个
target 变 11 个, `zenoh_router_client` 36 passed / 0 failed / 2 ignored。
这也回答了「整片豁免 vs 逐条裱糊」那条老争论: 判据是**根因是否已知**, 已知就具名跳过, 未知才整片。

② **覆盖边界**: `tls-init` 对已存在的 `tls/` 目录**从不替换** —— 六件齐备就跳过、不齐就 fail closed
报错, 两条路径都不会走到 rename。新用例 `tls_init_should_never_replace_existing_material_directory`
用目录 **inode** 做判据 (整目录 rename 会换掉 inode), 并在目录里放一个用户标记文件。
负对照: 把实现改成"先 `remove_dir_all` 再写"(即模拟重新生成), 该用例实测红; 恢复后 6 passed。
语义写进模块注释与 `specs/rdog-tls-plan.md`: 想重新生成必须由人删掉目录, 代价是显式的一步。

③ 载体同步: §3b 的 ubuntu 覆盖表 10→11、豁免段落改成具名跳过、§6 已知红那行改成
`TARGET_TEST_SKIPS` 口径, 并补上"具名跳过 vs 整片豁免"的选择判据。
- 提交: 待合入后补 (标题: `ci+fix(tls): ubuntu 豁免收窄成具名跳过, tls-init 覆盖边界补负对照 (RAI-464)`)
