# RAI-580 — 订阅声明不等 router 确认: 「传播窗口」改成可观测自检

> 票: RAI-580。关联: RAI-576 (ready sentinel 顺序, 已合), RAI-582 (sentinel 半行, 已合), RAI-524 (TLS link)。

### 2026-11-27 RAI-580: 声明传播改成可观测自检 (不说「留窗口」)

**病根**: `zenoh 1.8` 的 `declare_subscriber_inner` (`zenoh-1.8.0/src/api/session.rs:1704`) 只
`send_declare`, 不等 router 确认; `DeclareSubscriber::wait()` 只保证**本地注册**完成。所以
「声明之后立刻触发对端 pub」在跨进程 e2e 里可能丢首条消息 —— 之前测试里两种形态都在: 有的
`sleep 1s` 靠猜, 有的干脆不等。与 RAI-576 的 ready 顺序是两件事。

**自检** (`tests/support/propagation.rs`): 订阅声明之后, 于**同一 session** 声明一个 **queryable**
探针, 再用**另一个 session** 去 `get` 它; 回复必须经 router 路由到声明方再回来, 所以「答得出」⇒
router 已处理过这个 session 之前的 Declare (同一 session 的 Declare 按序到达) ⇒ 订阅声明对 router
可见。拿到就返回 (实测 9ms 量级), 拿不到在预算内重试 —— **没有等传播的固定 sleep**。

第一版用的是 liveliness token, 被 CI 判死: runner 上一条 5s 内 2391 次 query 都答不出, 另一条在
daemon `SIGSTOP` 之后反而报「可见」—— 客户端 session 会就本地 liveliness 状态作答。queryable
从构造上没有这条路。探针的回复另带 per-call nonce 并校验 keyexpr (只判 `is_ok` 时, 第三方在
同 keyexpr 下挂的 queryable 3.6ms 就能骗过它)。

**接入的 8 处** (`tests/zenoh_router_client.rs`): `keyinput` 订阅后 `@key` 一处; 五处 `to_control_key`
订阅后立即对 daemon 发 session-open query; agent reply 订阅后投 task 一处 (原来就是那处 `sleep 1s`);
agent 起来之前建 reply 订阅一处。整 target 从 ~200s 降到 **24s**。

**读数**:

| 项 | 读数 |
| --- | --- |
| `zenoh_router_client` 默认并发 20 轮 | **20/20 轮 `40 passed; 0 failed; 2 ignored`**, 每轮 23-24s |
| `declaration_propagation` (2 个测试) | 连跑 2 轮全绿, 每轮 ~45s |
| guarded 臂 20 轮首条投递 | 0 丢失 |
| 负对照: daemon `SIGSTOP` 时自检 | 返回 `router still does not report the declaration probe ... after 10 queries within 2s`; `SIGCONT` 后同一 keyexpr 重新可见 |

> 自检的承重性由「router 不可见 ⇒ 不通过」证明; 「传播未完成时会丢首条」这一层在本机未复现(750+ 次 0 丢), **未验**。

**诚实的边界: naive 臂在本机 loopback 上 0 丢 (750+ 次投递)**。四种加压形状都没复现出「声明后立刻
pub 会丢」:

| 形状 | naive 投递次数 | 丢失 |
| --- | --- | --- |
| 每轮新 session, 声明后立刻 put | 40 | 0 |
| 复用 session + `Session::put` 直发 (1/4/8 线程) | 400 | 0 |
| 声明前先灌 4 MB / 16 MB 大包占满发送队列 | 40 | 0 |
| 2 核机器上 4 个 CPU burner 争用 | 200 | 0 |

原因: `wait()` 返回时 Declare 已写进 socket, 而 pub 要走「客户端→router→订阅者」两跳, 本机来回路程
内声明总是先到。**本票不主张「自检修掉了本机可复现的丢包」**: 上游观测到的丢失发生在跨进程/慢链路,
自检的作用是把那类时序变成可观测条件。边界已写进
`docs/solutions/conventions/zenoh-pub-sub-declaration-propagation.md`。

**覆盖面**: 新 integration target `declaration_propagation` (`unix`) ⇒ ubuntu 13 / macos 13 / windows 2。

**未验**: macOS / Windows 运行时 (本机 Linux); 新 target 的 `SIGSTOP` 负对照用 `libc::kill`, 只在 unix。

**自检的实现换过一次, 原因写在代码里**: 第一版用 liveliness token, 本机两轮都绿, 但 ubuntu runner 上
两条测试全红且方向相反 —— 一条 5s 内 2391 次 query 都答不出, 另一条在 daemon `SIGSTOP` 之后反而报
「可见」(客户端 session 会就本地 liveliness 状态作答)。换成 queryable 探针后 SIGSTOP 负对照重新成立;
`declaration_propagation` 在 ubuntu 与 macos 都 `2 passed / 0 failed` (macos 49s, ubuntu 47s)。

**macOS runner 上 daemon 起不来一次**: 隔离 HOME 原来用 `temp_dir()` (macos 是 `/var/folders/...`
长路径), 换成 `/tmp/rdog-prop-<tag>-<pid>` 短根后通过; 并把「daemon 起不来」的 panic 改成带日志尾巴
(上一版只说 `never reported ready`, 拿不到服务端信息)。
