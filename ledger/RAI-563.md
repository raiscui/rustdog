# RAI-563 账本

windows 上「子进程有没有分配到控制台」的探针, 把**仪器坏了**读成了**被测性质破了**。

## 2026-11-26 探针编译失败与分到控制台分开

- 提交: 88962bb

`test (windows-latest)` 上 `control_flow::process::tests::flow_shell_should_not_allocate_a_console`
红了, 报的是 `left: Some(1)` / `right: Some(0)` —— 挡住的却是一个只改账本的 PR。探针用
`Add-Type -MemberDefinition` 在运行时编译 C#, **它自己会失败**; 于是「子进程真分到了控制台」与
「探针没编译起来」共用同一个退出码, 日志里分不出来 (同族断言另有两处: `control_actions/tests.rs`、
`task_control.rs`)。

- **读数先判仪器再判句柄**: `src/test_support.rs` 新增 `console_probe` —— 探针脚本里编译进
  `try/catch`, 但真正判「仪器可用」的是 `'Rdog.ConsoleProbe' -as [type]`: 只要探针类型没建起来
  (编译失败, 或失败没抛成终止错误), 一律打 `PROBE_COMPILE_FAILED` 并以专用退出码 `73` 退出。
  读数分三态: `NoConsole` / `Allocated(handle)` / `Unavailable(reason)`, 断言文本分别是
  「拿到了控制台 (GetConsoleWindow = N)」与「console 探针不可用: …」。
- **三份收敛成一份**: 三条 spawn 路径 (builder 建台标志 / flow step / 后台 task) 各自保留 —— 被测的
  本来就是各自的 spawn 实现; 但探针脚本与读数口径只有一份, 同一个仪器缺陷不再有三个副本。
  `run_powershell_probe` 的 UTF-16 stderr 兜底解码也并进 `console_probe::decode_stderr`。
- **模块不按平台门控**: 脚本是纯字符串、读数是纯判断, 只有「谁来 spawn」是 windows 的事。于是
  分类逻辑在 Linux job 上就能跑 —— 新增 6 条用例 (标记 / 专用退出码 / 句柄非 0 / 非 0 退出码 /
  stdout 不是数值 / 脚本与常量同值), 三个平台都覆盖。
- **负对照**: `console_probe_should_report_instrument_failure_not_console_allocation` 把真实脚本里的
  `GetConsoleWindow();` 改成 `GetConsoleWindow(;` 让 `Add-Type` 必然编不过, 再抓 `assert_no_console`
  的 panic 文本, 断言它点名「探针不可用」且**不含**「拿到了控制台」。没有这条, 修法只是换一种说法。

验证 (本机 Ubuntu, 跑不了 windows 运行时):

- `cargo test --bin rdog console_probe` → 6 passed / 0 failed (分类逻辑, 三平台可跑)。
- `cargo xwin check --tests --target x86_64-pc-windows-msvc` → 通过 (windows-only 测试代码编译干净)。
- 用 pwsh 7.4.6 跑真实脚本: 写坏的那条打出 `PROBE_COMPILE_FAILED` + `exit 73` (stderr 带
  `error CS1026: ) expected`); 正常那条在本机编过但 P/Invoke 失败, exit 0 且 stdout 为空 ——
  按读数落进 `Unavailable` 而不是假绿。
- **未验**: windows 上 `GetConsoleWindow()` 的真实读数、以及负对照用例在 `powershell.exe` 5.1 下的
  行为, 只能由 CI 的 `test (windows-latest)` 判。

## 2026-11-26 复核: 失败文案按阶段分开

- 提交: 802da69

`Unavailable` 原来只有一句笼统的「探针不可用」。复核要求它必须点明**哪个阶段**失败 —— 下一个读
日志的人要知道是编译没过、还是调用没过、还是根本没跑起来。于是脚本把调用阶段也单独标出来
(`PROBE_CALL_FAILED` + 专用退出码 `74`), 读数分成四句可分辨的文案:

| 读数 | 文案 |
| --- | --- |
| 标记/退出码 73 | `阶段一 编译失败: Add-Type 没把探针类型编出来` |
| 标记/退出码 74 | `阶段二 调用失败: 探针编出来了, 但 GetConsoleWindow() 本身抛错 (P/Invoke 层)` |
| 无退出码 | `脚本没有正常退出 (超时或被杀), 读数不成立` |
| 其它非 0 | `脚本以意外退出码结束 (exit N), 没有走到读数` |

配套用例从 6 条加到 7 条 (`call_failure_is_read_separately_from_compile_failure`, 并钉住超时与意外
退出码两种文案互不相同、脚本与两组常量同值)。

顺带清掉本模块引入的唯一一条 clippy 告警 (`% 2 == 0` → `is_multiple_of`): 复核前后
`cargo clippy --tests` 都是 167 条, `cargo build` 不编译 `#[cfg(test)]` 的 `test_support`, 0 条新增。
