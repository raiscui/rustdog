# RAI-705 账本

首块 ACK 30 秒未回: 客户端记 `chunks=0` / `bulk_bytes=0` / `aborted:true`, 而接收端已落 262,144 B
partial 且 SHA 等于源前缀。两侧状态差一个数量级 —— 不是路径判据问题 (没有 `iroh_direct_path_lost`),
是"回执没回来"与"对端做了什么"在客户端分不开。

## 2026-11-27 30 s 是客户端的每块 ack 预算; 回执没回 = 本端不知道对端做了什么 (不自动重拨)

- 提交: a18572a

### 30 s 的来处 (源码指认)

| 位置 | 事实 |
| --- | --- |
| `src/transfer_cli.rs:241` | `DEFAULT_CHUNK_ACK_TIMEOUT_MS = 30 * 1000`; 可由 `[file_transfer].chunk_ack_timeout_ms` 覆盖 (`src/config.rs:211/341`) |
| `src/transfer_cli.rs:771-785` → `src/control_iroh.rs:3185-3211` | 预算施加点: `set_read_timeout(30s)` → `write_message` → `read_message`; 是**逐请求**的读预算, 不是整次尝试的总额 |
| `src/control_iroh.rs:3223` | 超时文本带 `peer_state()`: `对端连接仍开着` / `对端已关: …` —— 这一行是分辨"app 预算先到"与"传输层先死"的唯一依据 |

票面怀疑的 `src/control_iroh.rs:1030` (`bracket.close(after)`) 在**首块路径上不会被调用**: 它是
`AttemptEvidence::finalize` 的一部分, 只在 `@file-end` / `@file-cancel` / 下载 `eof:true` / 门禁拒绝时
走到 (`serve_bulk_request` 的收尾 match, `src/control_iroh.rs:1178-1232`); 首块 `@file-chunk` 只走
`note_confirmed` (`:1182-1193`)。**"bracket 采样压住 flush" 不成立。**

daemon 首块路径上没有任何 30 s 级等待: `serve_lane` 读一行 (`:2556`) → `require_active` →
`serve_bulk_request`, 每块只做 `gate_bulk` (`route()` 是 `conn.paths()` 快照, `:1767-1777`; 最坏
20×50 ms = 1 s)、TRANSFERS 互斥 + **无 fsync** 的 append (`src/control_file_transfer.rs:403-471`)、
`note_confirmed`, 然后 `dispatch_outcome` 立即 flush 写回 (`src/control_session.rs:151-167`)。写回
自身的预算是 `max(frame_timeout_ms, frame_len/96 KiB/s)` (`src/control_iroh.rs:3525-3528`), 超时会
`FRAME_BROKEN` 报错而不是静默。

结论: 字节落盘而回执没回来, 客户端手里就只有"这次请求结果未知"这一件事。它**不能**被当成
"对端没做", 也不能被当成"可以从 0 重来"的许可。

### 交付 (观测, 不含自动重拨)

- `bulk_chunk_ack_unanswered` (`BULK_CHUNK_ACK_UNANSWERED`): 读回执超时**且连接仍开着**时的错误标记,
  语义只有一句"本端不知道对端做了什么"。命名空间是 `bulk_` 不是 `iroh_`: 它不是路径事实, 已登记进
  `specs/rdog-bulk-direct-only-spec.md` 的稳定码总表。
- daemon 侧 `iroh bulk ack verb=… transfer_id=… failed=… elapsed_ms=…` (debug): 只证明**本机**把应答
  写进了流 (dispatch → `write_all` 返回成功), 不证明对端收到。它的价值是把判别从两态变三态:
  有 ⇒ 本机写成功; 只有入站 `verb=…` 行 ⇒ 请求到了、应答没写成功; 两者都没有 ⇒ 这次请求没被这张
  lane 观测到。`RDOG_LOG_LEVEL=debug` 是这三行的前提。
- 确定性测试: `a_read_timeout_on_a_live_connection_maps_to_the_ack_unanswered_code`
  (`src/control_iroh/lane_runtime_tests.rs`, 真 quinn 流 + 对端读走请求、永不回执、连接保持开着)
  钉住"读超时 + 连接仍开 ⇒ 该码"; `the_daemon_logs_both_halves_of_the_ack_discriminant`
  (`tests/iroh_bulk_abort_resume.rs`) 钉住三态判别所需的入站行与 ack 行确实打出来。
- **不含自动重拨**。评审 (固定 head `7665595`, 1 severe / 6 medium / 1 low) 指出: 丢失成功的
  `@file-end` 回执后重开, daemon 没有"已提交结果"可回放, 第二次提交会把成品**替换**掉; 另有
  `--restart` 被重放、open 已执行时 ID 丢失、旧 handler 仍可追加并让新 lane 删掉有效 prefix、
  按文案子串匹配、`attempt_id` 复用覆盖首轮快照五条。同 ID 幂等续传归 **RAI-711**, 退出判据即那几条。

### 那段 ubuntu 红 (`a_put_killed_mid_upload_resumes_on_the_first_retry`) 的归因

**结论: 属 (c) 环境/时序, 不是本票改动引起 —— 但"哪一步超预算"在 CI 日志里判不了, 这里有明确证据边界。**

- 同一 head `7665595` 复跑 **7/7 全绿** (2026-11-28T01:13Z); 本地最终树 5/5 绿。同一份代码同平台先红
  后绿 + 本地稳定绿 ⇒ 不是确定性缺陷。
- 原失败那次的客户端输出只到 **3 个握手 session** 就 `exit=1`, 且**没有任何进度行或错误行**出现在
  panic 消息里 —— 而 GitHub 的 `--log-failed` 在客户端错误行之前就截断了, 所以"死连接没被放掉"与
  "重拨预算不够"这两种成因**都无法从这份日志判定**: 3 次尝试 < 9 次预算上限, 说明它不是把 18 s 用光,
  真实最后一跳的错误文本没留下来。daemon 那半边 (`daemon:` 段) 同样没进 `--log-failed` 输出。
- 因此这条不当作"已知外部缺陷"放行, 只记录为**一次不可复现的时序性红**, 并靠本票新增的三态判据
  (`verb=@file-chunk` + `iroh bulk ack …` + `RDOG_LOG_LEVEL=debug`) 让下一次同类红可定因。
