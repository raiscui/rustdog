### 2026-11-26 RAI-476: 客户端走 iroh 准入 lane 传 bulk + relay 括号采样

- 提交: 7f7f83a

`rdog control --transport iroh --put/--get` 第一次真的走 iroh 准入 lane: 一条长连接承载七条
bulk 行, 握手复用 PTY 客户端的 `admit_lane` (不新造手续), 租约续期与 PTY 同一条线程。客户端
能力从 `NOT_PATH_AWARE` 改成 `PATH_AWARE_CHECKED_PER_CHUNK` (path_aware / pin=false /
checked_per_chunk=true); TCP/WebSocket/Zenoh 不动, 仍是 `not_applicable`。

括号采样在客户端有了生产者: open 前 `before`、终态后 `after`, 换算抽成 `relay_bracket` 与
daemon 侧共用一份 (读不到或在场集合对不上 → 四个 null)。`established_direct` 按 transfer_id
记并在 open 复位, 上传方向的 `iroh_direct_path_lost` 因此可达 (用例: 边界采样从 direct 掉 relay
时块一个都没发出、保留半成品不 cancel, 按 §2.5 B3 供续传)。

daemon 那一半不再丢: `@file-end` / `eof:true` 的 `@file-read` 响应里的 `evidence` 原样写到
`--bulk-path-json` 同目录的 `bulk-path.daemon.json`; 收不到就不写, 只 stderr 说明, 让 join 落到
`bulk_path_endpoint_missing`。规格补 §5.1 (客户端专属小节, 未动 §4.3 的 join 段)。

措辞: 客户端能主张的是测量事实 ——「括号两点之间该连接的 relay path 不存在, 或增量低于空闲噪声
量级」, 不是"relay 链路上字节为零"。`stats().udp_tx/rx.bytes` 含 ACK/keepalive/PATH_CHALLENGE,
空闲 relay path 自己也会涨, 所以 F8 先量了分母: 30 s 空闲 (不传 bulk) tx +757 B / rx +226 B,
约 25 B/s / 7.5 B/s (2026-11-26 真机单次, Linux 客户端 → razer daemon, `path_class=relay`)。
这份基线无法用出货 CLI 取得 (`--put` 在 relay 上 open 即被门禁拒, 括号建立后立刻终态), 来自测量分支
`capy/rai476-relay-baseline` @ `e3ae713` 的 `rdog iroh relay-baseline`。
未验: 真机跨网与 relay 拓扑 (回环上不可能有真实 relay, 只到 direct)。

用例侧的收尾也在这一个提交里: "中途掉 relay"那条用例在生产上要保留半成品供续传 (§2.5 B3), 但会话表
是进程级单例, 并行的回收用例把 `now` 推到未来时刻时会把它判成空闲回收, 于是别人的 `reaped` 计数变成 2
—— 用例按 `transfer_id` 调 `forget_sessions_for_tests` 收干净, 断言一条没改。(触发这次 CI 红的另一半
"读表/改表与回收被两把锁分开保护"已由 main 上的 RAI-411/433 线修掉。)

实测: 收尾前 `cargo test --bin rdog -- transfer_cli control_file_transfer` 8 次红 2 次; 收尾后同样
组合 12 次全绿, 全量 `cargo test --bin rdog` 连跑 3 次均 1279 passed / 0 failed / 4 ignored。

### 2026-11-26 RAI-476 评审: 帧预算随帧长、括号并集对账、id 复用落到续传

- 提交: 1b7e191

三条 high 都出在"能出结论的地方恰好漏了一条":

1. **帧写预算与块大小** — 5.03 MB 的默认块 base64 后约 6.7 MB, 而 `noq` 单流窗口 1.25 MB, 固定
   3 s 预算在 2.2 MB/s 以下必超时并把 lane 打成 poison。这条 lane 的**上传**收到 256 KiB/块,
   **下载**受响应行 48 KiB 预算约束是 36096 B (`run_get_inner` 的 `.min(response_payload_bytes())`),
   预算改成 `max(frame_timeout_ms, 帧长 / 96 KiB/s)`。不靠使用者抬 `frame_timeout_ms`。
   (本节原文写"256 KiB/块 (两个方向)"是错的: 下载那一侧从 `1b7e191` 起就按响应预算切。)
2. **括号对账** — `before` 只有直连时集合为空, `all()` 真空成立, 于是"边界上短暂 fallback 走掉一段
   字节"会被读成四个 0 并判 `relay_bytes_zero`。改成用**本次见过的 relay path 并集** (open 前 +
   每个边界采样 + 终态) 对账; 空并集不豁免 (两个计数仍须都在)。
3. **失败后的会话** — lane poison 时 cancel 发不出去, daemon 的会话占着目标推导出的暂存名, 换新
   transfer_id 会被 `file_transfer_path_in_use` 挡到窗口过期。`--put` 的 id 按 (本地, 目标, 远端)
   记在 `~/.rdog/bulk-transfer-ids.json`, 下一次自然落到 `resume:true`; 提交后忘掉; `--restart` 换新。
   `--get` 不复用并在规格里写明理由。

四条低危: 错误回执上的 daemon 半快照不再丢; 每次尝试前删掉上一份 `bulk-path.daemon.json`; 下载方向
补上每块边界门禁; 成功路径只写一次快照。新增 9 条用例 (客户端 6、daemon 1、帧预算 2)。

### 2026-11-26 RAI-476 复核 D1-D5

- 提交: 416e408

**D1** 三个地方对 chunk 尺寸的说法互相矛盾, 其中两处是假的: iroh lane 上上传 256 KiB, 下载受
响应行 48 KiB 预算约束是 36096 B —— 不共用同一个值, 因为撞的是两条不同的预算。规格算术段补上
下载方向的结构上限写成公式 `单块载荷 / 每块周期`。三个 cap 分开写: 协议通用 `chunk_payload_bytes()`
= 5,033,160 B; 上传**有效** cap = `min(chunk_payload_bytes(), IROH_CHUNK_PAYLOAD_BYTES)` = 262,144 B;
下载有效 cap = `response_payload_bytes()` = 36,096 B。**模型值** 36096 / 0.42 s = 85.94 kB/s (0.42 s 是
模型输入, 不是独立测出的 RTT) 与**实测均值** 20 MiB / 248 s = 84.56 kB/s 分列, 不合并成一个数。

**D2** `--restart` 换新 id 但没先收旧会话, daemon 的"别的 id 持有同一暂存路径"检查先于
`resume:false` 的清理; 更糟的是 store 在尝试之前就被覆盖, 于是不带 `--restart` 的重跑也被挡,
而错误文本还在许一个已经用不到的 id。现在 restart 先 `@file-cancel`, store 只在 open 被接受后写。

**D3** store 是 load + 覆盖写: 并发会丢条目, 退回的正是本 PR 要消灭的 `path_in_use`。改成临时
文件 + rename, 写前重读合并。**D4** 键补上 target —— 同一本地文件发往两台主机是两次传输。

**D5** 一条 relay path 若只活在一个块间隔里, 并集也看不见它; 这条残余写进 §3.5 与 §4.2, 与结论一起引用。

新增 2 条用例 (restart 收旧会话 + open 失败不许诺续传), 改写 1 条 (#4 的替身只在终态错误上挂证据)。

### 2026-11-26 RAI-476: 写清 id store 没有在途 owner

- 提交: b98efa4

`--restart` 按 store 里的 id 发 `@file-cancel`, 而键 `(target, local, remote)` 不含进程身份, 也没有
"这条 id 归谁用"的守卫 —— 同一键上有并发进程时, 那条在途会话会被一起取消。这一格这轮只**说清**

restart", 反而让这一格看起来闭合了。

### 2026-11-26 RAI-476: id store 改成一键一文件 (D3 复核)

- 提交: 44a4ae6

复核把上一版做实了: 共用一张表时 `load → insert → save` 没有互斥, 200 轮丢一条键 **144 次**;
temp + rename 只保"读者看不到半张表", 挡不住"读-改-写丢更新"。临时名只带 pid 也不行 —— 同进程
的两个并发写共用暂存名, 能把半份文件 rename 到位 (`trailing characters` / `No such file`)。

现在是 `~/.rdog/bulk-transfer-ids/` 下一个键一个文件, 两次写入只碰各自那份; 暂存名后缀是
`pid.<原子计数器>`。自测 (线程形态, 不是进程): **两个独立 store 实例**各写一条不同键跑 200 轮,
**200 轮 / 200 次都对**, 该用例连跑 5 次全绿; 再各写 300 次 burst, 仍无 `trailing characters` /
`No such file`, 且目录里不留 `.tmp`; 截断一个键只作废它自己。读取路径另外校验文件里的真实键:
撞车按缺失处理 (fail-closed), 不把别人的 id 当本键返回。
文档同步: 规格 §5.1 存储形态、`--restart` help、`TransferIdStore` 文档; owner 租约引用 RAI-526。

### 2026-11-26 RAI-476: 读数必须带两端构建身份

**记账模板 (A 类读数一条一行, 缺字段按未验收处理)**:

### 2026-11-26 RAI-476: build 探测限定 workspace 根 + join 三态 + 下载上限改公式

- 提交: 待合入后补 (标题: `fix(bulk): build 探测限定 workspace 根 + 回执列序 + join 落 build 三态 (RAI-476 复核)`)

### 2026-11-26 RAI-476: 共享 target 的构建身份限制 + CI 显式注入

- 提交: 待合入后补 (标题: `fix(build): 顶层目录判定容忍合法尾空格 + CI 显式注入 GIT_SHA (RAI-476 复核四)`)

**共享 `CARGO_TARGET_DIR` 且跨 checkout 构建时, 构建身份可能沿用上一次的值** —— Cargo 在包指纹相同时
根本不会咨询 build.rs 的 `rerun-if-changed`, 所以这不能靠 build.rs 修。两条处置:

1. **CI 侧显式注入**: `.github/workflows/ci.yml` 的三段 `Build` 步骤设 `GIT_SHA=${{ github.sha }}`
   (走 `env!("GIT_SHA")`; `src/build_info.rs:10` 就是它 —— build.rs 每次都以 `cargo:rustc-env=GIT_SHA=…`
   注入, 取不到 git 时注入 `unknown`, 所以编译期 `env!` 是安全的, 不存在"宏没定义"那种风险),
   CI 读数不依赖 build.rs 的缓存语义。
2. **本地侧只有一条限制**: 共享 target 跨 checkout 时 Cargo 不重跑 build script, 身份可能沿用上一次的
   值 (判据: 第二次 `Fresh` 且 ELF 沿用旧 sha ⇒ 该读数不得用于跨版本对比)。「设了 `GIT_SHA` 却没重编」
   这条**不成立**: **改构建命令上的 `GIT_SHA` 会自动重编**(Cargo 报 `the env variable GIT_SHA changed`
   并重跑 build script), 实测 `GIT_SHA=aaaaaaa cargo build` → ELF 里 `client aaaaaaa`; 换 `bbbbbbb`
   再建 → `bbbbbbb`; 去掉再建 → 当前 HEAD 短 sha。**仅改启动环境无效**(`GIT_SHA=aaa ./rdog` 不重编,
   仍读上次烘进二进制的值; 复核负对照: 用 `GIT_SHA=aaaaaaa` 启动一个 `bbbbbbb` 的二进制, 输出仍是
   `bbbbbbb`)。
3. **六个 job 都注入**: `test (os)` 也会在缓存未命中时编译, 只给 `build` 注入会让那些二进制的身份是
   `unknown` —— 同一份代码在不同 job 里身份必须一致, 否则一比就是假的 mismatch。
