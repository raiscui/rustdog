# RAI-524 — TLS link 的读写任务可同时进入同一 rustls Connection

> 票: RAI-524。关联: RAI-464 (归因拆分), RAI-564 (残余的客户端 session 缺陷)。

### 2026-11-26 RAI-524: 病根证实 + 互斥修法落地

`zenoh-link-tls` 1.8.0/1.10.2 的 `LinkUnicastTls` 用 `UnsafeCell<TlsStream>` + **两把不同**的锁
(`read_mtx` / `write_mtx`) + `unsafe impl Sync`, 读写任务可同时对同一 rustls `Connection` 取 `&mut`。
判别探针 (只读原子计数, 不加锁): **失败写 15/15 都伴随并发读在场, 成功写的对照比例 42%**
(15 次全落 42% 一侧, 偶然概率 3e-6); 指纹 = daemon 侧 `write #4` + `handshake not complete`。

修法: 读写共用一把锁, 两侧都改「锁内非阻塞 poll + 锁外自持 waker 等待」, `close()` 锁内只做非阻塞
flush/shutdown。
- 对照 A (两把锁 + 读短临界区): 8/8 轮红 —— 窗口变短无用;
- 对照 B (单锁 + 阻塞读): 20/20 失败、2s→121s —— 会饿死写;
- 本修法: **1200 次连接里 `handshake not complete` 0 次**, 吞吐 90ms/次 (基线约 100ms/次)。

残余失败 (约 1/400) 是 RAI-564 的指纹 (daemon 无错误行 + client session 提前关闭), 不同源。
- 提交: 待合入后补 (标题: `fix(tls-link): 读写共用一把锁且都不跨 await 持锁, 消掉 TLS link 的并发访问 (RAI-524)`)

### 2026-11-27 RAI-524: 空闲 CPU 归因、close 语义收口、假计数器清零、回归测试落地

**复核的 98% 空闲 CPU 是哪一条**: 唤醒许可被还回信号量 (`SemaphorePermit` 未 `forget`), 等待分支
永久就绪, 空闲读任务在自己的循环里空转。**同机同仪器的负对照** (把 `permit.forget()` 改回
`drop(permit)`, 只改这一处, 其余不变):

| 版本 | 空闲 PTY 链路的 daemon CPU (5s 采样) |
| --- | --- |
| 许可被还回 (40631a2 之前的形状, 复核量到的正是它) | **98.4%** (492 ticks / 5.00s) |
| 许可被消费 (`296f3bd` 起) | **0.6%** (3 ticks / 5.00s) |

同路径走 `tcp/` 时两版都是 0.6% —— 与复核的「tcp 0%、原版 crate 1%」一致。也就是说复核量到的是
`296f3bd` 已经修掉的那条 severe; 本轮的交付是**让它可回归**: `tests/tls_link.rs` 里
`idle_pty_link_should_not_burn_daemon_cpu` 起真 daemon + 长命 `--pty -- sleep 8` 链路, 采样
daemon 各线程的 `/proc/<pid>/task/*/stat`, 2s 静默窗断言 < 0.3 核时。读数: 修后 **0.00s/2.00s**,
把许可改回还回后 **1.91s/2.00s** (红)。

**close() 语义**: 40631a2 的 `close()` 已经有"有界推完 flush"的循环 (296f3bd 引入), 所以「flush
一次 Pending 就丢尾部」这一条**在 40631a2 上已不成立**; 仍然存在的是它之后那段: 一次非阻塞
`poll_flush`/`poll_shutdown` 后**无条件 `Ok(())`**, shutdown 的 Pending 与错误都被吞掉。本轮改为:
推完 flush (有界 5s, 报告超时) → 等 shutdown 真正完成 (同一 deadline, 错误照样传播) → 取消
`closed`。回归测试 `close_drains_accepted_records_under_backpressure` (8 MiB 载荷 + 对端慢读)
读数: 修后 `received=8388608/8388608`; 把 `close()` 换回 `139e19f` 的单次 poll 形态后
`received=8321370/8388608` 且 **close 仍报 Ok** (丢 67,238 字节) —— 红。

**同向 gate 曾经只覆盖单次 poll**: `read_gate`/`write_gate` 原先加在 `write_short_critical_section`
/`read_short_critical_section` 里, 而 `write_all` 是循环调用它的, 于是**分片之间会放锁**, 两路并发写
仍能交错。新回归测试先把它抓了出来: 两路 1 MiB 帧并发写, 对端慢读, 收到的流第一个长度前缀变成
`0xAAAAAAAA`。修法: gate 提到整调用层 (`write`/`write_all`/`read`/`read_exact` 各持一次)。读数:
修后两帧完整同质; 拆掉整调用 gate 后同一断言再红 (长度前缀被破坏)。

**假计数器全部删除**: `LOCK_HELD_ACROSS_AWAIT`/`note_violation` 从未被调用 (0 是真空转),
`POLLS_IN_LOCK`/`OUTSIDE_WAITS` 写而不读, `FALLBACK_WAKEUPS` 恒 0 是因为 `biased` 让兜底计时器
永远轮不到, `read_mtx` 是死字段。它们连同 100ms 兜底重试一起删掉: 唤醒改用信号量语义 (唤醒发生在
注册之前也不丢) + `CancellationToken` 承担取消, 所以不再需要"每隔 100ms 重试"这种既不是取消也
不是健康的机制。字段改名 `tls_mtx`, 注释同步。

**取证补强 (medium 3)**: 每次 attempt 与真实 TLS 连接数分开计 (`scripts` 侧脚本见
`handoffs/RAI-524/tls_evidence.py`: 客户端 exit code/pong/耗时逐次记录, daemon 侧数
`Accepted TLS connection` 与 `handshake not complete`)。读数 (本机 2 核, 100 次连接/轮, 修后二进制):

- attempt 100 / daemon `Accepted TLS connection` 100 / `handshake not complete` 0 / 丢 ack 0;
