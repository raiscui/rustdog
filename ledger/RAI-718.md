# RAI-718 跨网直连探针

## 2026-11-28 同 socket QNT 现场试验

- 提交: 4ad72f4

候选分支 `capy/rai718-direct-probe`，未合入。客户端的 `direct_connect_timeout_ms` 由
[`ClientConfig::direct_connect_budget`](../src/control_iroh.rs) 定义，独立于帧、目录和准入预算。
显式 `probe_direct_via_relay` 让 `@ping` 在同一数据端点做 UDP/QAD 和
QUIC NAT Traversal，等选出具体直连地址再开流。服务端只在 opt-in 的服务端点接受
`DIRECT_PROBE_ALPN`，拒绝非准入身份；PTY/bulk 不进入该探针，原路径门禁不变。

A 与 D 同源真机：D (家庭 Wi-Fi) → A (云 EIM + APDF) 在两轮扩展预算和一轮默认预算均收到
同 ID 直连 pong；A → D 在同样三轮交换了候选，双方均向对方公网候选发包，但无验证成功的
直连，未发 ping。双向 relay-only 正对照均有 pong，未列入允许列表的探针被拒。A → D 的
证据只定位到公网候选未完成验证，不能从超时判 D 的过滤规则。详见 Captain Drive 的
`reports/RUST-39.md` 与 `handoffs/RAI-718/receipts/`。

本实验不证明 bulk 直连改进，不把直连时刻采样当作路径钉住。Linux 定向 `control_iroh::`
测试 74 passed / 0 failed / 2 ignored；真机 A 与 D 只跑 ping。

## 2026-11-28 启用已准入探针的同 endpoint 反拨

- 提交: b9fcae9

[`dial_direct_probe_reverse`](../src/control_iroh.rs) 在已准入的 ping 连接上至多反拨一次，
目标是已认证的对端身份及配置的 relay，使用原接收 endpoint。反拨专用 ALPN 不承载应用流；
反拨无法建立时仍执行原 direct-only ping accept，不允许 relay 代发 ping。bulk 接线和门禁不变。

同源正式 CLI：A→D 4/10，D→A 10/10，20 个槽位均只反拨一次。A→D 余下 6 轮双方均向对方
公网候选发出 UDP，但未验证出 direct。未列入允许列表的探针反拨 0 次；不支持反拨的旧候选
仍能从新 daemon 收到 direct pong。独立 `--put` 正对照 65536 B 双端 SHA-256 相同、双端 join
`relay_bytes_zero:true`；relay 负对照 `iroh_direct_path_unavailable`，发送端 0 字节、服务端无目标和
partial（缺服务端快照，不写成双端计数）。源码与真机原始回执见 Captain Drive
`reports/RUST-39.md` 和 `handoffs/RAI-718/receipts/bilateral/`。
