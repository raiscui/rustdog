# RAI-576 账本

`zenoh_router_client` 的 agent mailbox 用例在多条互不相关的 PR 上间歇红。本票拆成三条互不
排斥的解释, 本 PR 只落地 (a)。

## 2026-11-27 ready sentinel 必须晚于 mailbox 通配 sub 声明

- 提交: 28ccd32

**(a) 确定性缺陷 (本 PR 修的就是这条)**: `src/zenoh_control.rs` 的
`zenoh router daemon ready` 打在 agent inbox / card 通配 sub 声明**之前**, 而 e2e 与运维
脚本全拿这一行判「可以投递」。于是「ready」的实际含义是「router 起来了」, 不是「mailbox
能收」—— 按它投递会撞进订阅尚未声明的窗口, pub 无缓存, 丢了补拉不回来。

- 修: ready 挪到两条通配 sub 声明之后; 两条声明各加一行 `agent card|inbox 通配 sub 已声明`,
  让启动顺序能从日志自证。
- 确定性读数 (逐轮记两个 marker 的到达时刻, 带饱和加载): 修复前 **10/10 轮 ready 先、声明后**
  (本机间隔 0.01ms); 修复后 **8/8 轮声明先、ready 后**。
- 守卫 `daemon_ready_should_be_logged_after_mailbox_subscriptions` 断言这个顺序。**负对照:
  把 ready 挪回 v0 位置, 该用例立刻红** (`card=1917, inbox=1987, ready=1364`); 这正是这一族
  缺的东西 —— 出事的本地化用例只会「有时」红, 拿它们当回归证据等于靠运气。
- 顺带: 两条出事用例的失败文案补上 daemon 日志与最后读数 (原来 `assert!(saw_single)` 什么都不
  打, CI 上只能猜); 新增零延迟探针
  `mailbox_should_accept_a_publish_immediately_after_ready`。

**(b) 端口撞号 (RAI-568, 已基本消除, 本 PR 不含)**: 客户端可能连进**另一个** daemon ⇒ 症状正好
是「投了但补拉不到」与「查询挂到超时」。`#180` + `#182` 之后 `allocate_tcp_port` 是唯一分配实现。
若这一族仍复现, 说明还有第四因。

**(c) 传播那一跳没有等待 (未修, 待开票)**: zenoh 1.8 的 `declare_subscriber_inner`
(`~/.cargo/registry/.../zenoh-1.8.0/src/api/session.rs:1704`) 只 `send_declare` **不等 router
确认**, `.wait()` 只是本地注册。所以「修复把日志挪到声明之后」关的是**顺序**, 不是**传播**。
deterministic 的解法是自检 (声明后对本端 keyexpr 发一次 query 直到自己答得出, 再触发被测流程),
不是给测试加 sleep。

## 未验 (照实写)

- **随机红未验**: 本机复现率 **0/50** (整 target `--test-threads=16` 20 轮 + 零延迟探针 30 轮)。
  压不上来就不能写「改完 N 轮到 0」—— 上面给的是 (a) 的顺序读数与负对照, 不是「这一族不再红」。

  跑同样命中它 —— 是该 target 的**另一个**随机卡点, 与本票无关, 未处理、未豁免。
